# Powdergame — User Vision

> 이 문서는 **“무엇을 구현할 수 있는가”보다 “무엇을 만들고 싶은가”를 먼저 고정한다.**
>
> 기술적 제약 때문에 제품 비전을 축소하기 전에, 먼저 원하는 세계를 최대한 크게 정의한다.

## 1. 출발점

이 프로젝트에서 가장 중요한 영감은 두 가지다.

### Doodle God에서 좋아하는 것

- 원소와 개념을 **조합하는 즐거움**
- 무엇이 나올지 모르는 **발견의 즐거움**
- 세계를 처음부터 만들어간다는 **신이 된 느낌**
- 단순한 정답 찾기보다 “이것도 되지 않을까?”라고 상상하게 만드는 구조
- 한 발견이 다음 발견을 계속 열어주는 연쇄성

### Powder Game에서 좋아하는 것

- 물질을 실제 공간에 직접 놓고 만지는 즉각성
- 물, 불, 모래, 바람, 금속 등이 **위치와 상태에 따라 실제로 상호작용**하는 것
- 개발자가 일일이 연출하지 않은 사건이 작은 규칙의 충돌에서 생기는 것
- 정답 없이도 그냥 만지고 관찰하는 것 자체가 재미있는 샌드박스성

Powdergame은 이 둘을 나란히 붙이지 않는다.

**Doodle God의 발견이 Powder Game의 실제 세계 안에서 일어나도록 만든다.**

---

## 2. 궁극적인 플레이어 판타지

플레이어는 단순히 재료를 선택해 뿌리는 사람이 아니다.

처음에는 흙, 물, 불, 공기 같은 기초적인 것만 만지다가 점점:

```text
물질
→ 에너지
→ 화학 반응
→ 생명
→ 생태계
→ 기계
→ 정보
→ 언어
→ 사회
→ 문명
→ 신앙과 신화
→ 인공지능
→ 시간과 공간
→ 세계 법칙 자체
```

를 건드릴 수 있게 된다.

최종적으로는 **“모든 원소를 발견한다”**가 아니라:

> **내가 상상한 가설을 세계에 던지고, 세계가 실제 결과로 대답하게 한다.**

가 목표다.

---

## 3. 범위는 현실 세계에 한정하지 않는다

최종 세계는 가능한 한 넓은 인간의 상상력을 받아들일 수 있어야 한다.

- 물리, 유체, 열, 압력, 중력, 전기, 자기
- 화학, 연소, 산화, 용해, 촉매, 결정화
- 지질, 침식, 화산, 지층, 광물
- 기후, 대기, 구름, 비, 바람, 계절
- 생물, 세포, 식물, 동물, 균류, 미생물
- 유전, 돌연변이, 진화, 공생, 생태계
- 기계, 에너지, 산업, 회로, 컴퓨팅
- 언어, 기억, 지식, 정보, 네트워크
- 인간·에이전트, 사회, 경제, 문화
- 정치, 갈등, 전쟁, 협력, 제도
- 종교, 신앙, 신화, 의식
- AI, 자동화, 자율 시스템
- 천문, 행성, 우주, 우주 환경
- 마법, 마나, 영혼, 룬, 저주
- 시간, 차원, 확률, 인과관계
- 꿈, 소문, 질서, 혼돈, 기억 같은 추상 개념
- 초현실적·판타지적·사용자 정의 법칙

중요한 것은 이 목록의 숫자가 아니다. **서로 다른 계층이 실제로 서로 영향을 주는 것**이 중요하다.

예를 들어:

```text
물 → 증기 → 압력 → 터빈 → 전기 → 회로 → 계산 → 네트워크 → 문명 → AI
```

같은 방향뿐 아니라:

```text
집단의 기억 → 신앙 → 성지 → 마나장 → 중력 변화 → 새로운 생태계
```

같은 반대 방향도 가능해야 한다.

## 4. 핵심 설계 원칙

### 4.1 원소 숫자보다 관계의 차원을 늘린다

`1,000 elements` 자체는 목표가 아니다.

물질 하나가 온도, 압력, 산소, 전기, 생물, 정보, 마나, 시간 같은 여러 시스템과 관계를 맺을 수 있을 때 깊이가 생긴다.

### 4.2 레시피와 물리 시뮬레이션을 분리하지 않는다

초반에는 직관적인 조합이 있어도 좋다.

```text
물 + 불 → 증기
```

하지만 점점:

```text
물 + 열 + 밀폐 공간
→ 증기
→ 압력
→ 구조물 운동
→ 발전
```

처럼 **실제 현상을 만들면서 발견하는 게임**으로 변해야 한다.

### 4.3 모든 것을 “픽셀 원소”로 만들지 않는다

세계는 최소한 다음 종류를 구분한다.

- **Matter / Particle** — 공간을 차지하는 물질
- **Field** — 온도, 압력, 산소, 전위, 마나처럼 퍼지는 값
- **Agent** — 상태, 기억, 목표를 가진 생명/AI
- **Concept** — 언어, 문명, 신앙, 전쟁처럼 의미로 존재하는 것
- **Meta Rule** — 시간 배율, 확률, 중력 방향, 반응 법칙 등 세계 규칙

그래야 모래부터 문명까지 억지 없이 한 세계에 넣을 수 있다.

### 4.4 개발자가 예상하지 않은 현상이 나와야 한다

콘텐츠를 전부 스크립트로 만들지 않는다.

좋은 시스템은 단순한 국소 법칙이 충돌해 **개발자가 직접 작성하지 않은 결과**를 만들어낸다.

프로젝트의 가장 중요한 검증 질문은:

> **플레이어가 개발자가 의도하지 않은 재미있는 현상을 실제로 발견하는가?**

이다.

### 4.5 과학적으로 완벽한 것보다 내부적으로 일관되어야 한다

현실 물리와 화학은 강한 기반이다. 하지만 이 게임은 학술 시뮬레이터가 아니다.

판타지·신화·추상 개념까지 들어오더라도 플레이어가:

> “이 세계의 규칙에서는 그래서 이런 일이 일어났구나.”

라고 이해할 수 있으면 된다.

즉 **정확성보다 인과관계와 일관성**을 우선한다.

### 4.6 강력한 것은 단순 너프가 아니라 외부효과를 가진다

불은 강해서 숫자를 깎는 대신 산소를 먹고 열과 연기를 만든다.

문명은 강해서 약하게 만드는 대신 자원을 소비하고 오염, 갈등, 기술 같은 다른 시스템을 낳는다.

강력한 시스템일수록 세계에 더 큰 파문을 남겨야 한다.

### 4.7 복잡해질수록 “왜?”를 보여줘야 한다

창발성이 커질수록 원인을 이해할 수 있는 도구가 필수다.

어떤 생물이 죽거나, 문명이 탄생하거나, 갑자기 폭발했을 때 게임은 가능한 한 인과관계를 설명할 수 있어야 한다.

**Causal Inspector**는 부가 기능이 아니라 핵심 UX 후보로 본다.

### 4.8 쉬운 바닥 + 거의 없는 천장

처음 플레이하는 사람은 브러시로 모래와 물을 뿌리는 것만으로 재미있어야 한다.

반대로 깊게 파는 플레이어는 회로, 생태계, 진화, 문명, 룰 에디터까지 갈 수 있어야 한다.

복잡성은 처음부터 UI에 쏟아붓지 않고 **발견과 관찰 도구를 통해 자연스럽게 열린다.**

## 5. 발견과 진행

진행은 다음처럼 발전한다.

1. **직접 조합** — 물 + 불 → 증기
2. **조건부 조합** — 물 + 열 + 밀폐 → 압력
3. **구조 발견** — 압력 + 움직이는 구조 → 기계적 일
4. **시스템 발견** — 터빈 + 자기장 + 전도체 → 발전
5. **창발 발견** — 충분한 신호 처리가 일어나면 “계산” 발견
6. **메타 발견** — 세계 규칙 자체를 관찰·수정

후반으로 갈수록 레시피 버튼과 실제 시뮬레이션의 경계가 사라지는 것이 이상적이다.

진행 보상도 단순히 “더 좋은 원소”를 주기보다:

- 온도/압력/산소 오버레이
- 현미경
- 유전자 분석
- 반응 그래프
- 자동 실험
- 타임라인과 Rewind
- World Fork
- Rule Editor

처럼 **세계를 이해하고 창조하는 능력**을 확장한다.

---

## 6. 플레이는 정답보다 실험이어야 한다

퍼즐이 들어가더라도 하나의 레시피를 맞히는 방식보다 **조건을 만족시키는 방식**을 선호한다.

예:

- 사막에 비를 내려라
- 전선 없이 신호를 보내라
- 태양 없이 숲을 유지하라
- 스스로 수리되는 댐을 만들어라
- 불에 사는 생물을 만들어라
- 전쟁하지 않는 문명을 유지하라
- 규칙 하나만 바꿔 세계를 멸망시켜라

해법은 여러 개여야 하며, 엉뚱하지만 세계 법칙상 성립하는 해법도 인정해야 한다.

## 7. 플랫폼과 구현 방향

### 목표

브라우저, macOS, Windows를 **서로 다른 세 게임으로 만들지 않는다.**

플랫폼마다 허용 가능한 계산량과 표현 수준은 달라도, 가능한 한 같은:

- 세계 모델
- 원소/규칙 데이터
- 발견 체계
- 저장 철학
- 시뮬레이션 의미

를 공유한다.

### 개발 순서

#### Stage 0 — HTML Concept Prototype

이미 시작한 단계.

목적은 엔진 기술을 증명하는 것이 아니라:

- 직접 만졌을 때 재미있는가
- 발견 로그가 재미를 더하는가
- 조합과 공간적 반응을 함께 두는 컨셉이 성립하는가

를 가장 빠르게 검증하는 것이다.

#### Stage 1 — Browser Play Lab

브라우저에서 바로 실행하고 공유할 수 있는 형태로 물리·반응·발견 규칙을 빠르게 실험한다.

이 단계에서 순수 JavaScript CPU 구현을 최종 엔진으로 간주하지 않는다.

#### Stage 2 — Shared Simulation Core

컨셉이 검증되면 시뮬레이션을 UI에서 분리한다.

현재 유력한 방향은 **Rust + GPU compute/WebGPU 계열의 공용 코어**지만, 기술 선택 자체보다 다음 조건을 우선한다.

- 결정론적 재현 가능성
- 데이터 기반 원소/반응
- active chunk / sparse update
- 멀티스케일 시뮬레이션
- 플랫폼별 백엔드 교체 가능성
- 브라우저/네이티브가 동일한 의미 체계를 공유

#### Stage 3 — macOS Native

같은 코어를 바탕으로 브라우저보다 더 큰 세계, 더 높은 품질의 유체/열/장 계산, 장기 생태 시뮬레이션 등을 연다.

#### Stage 4 — Windows Extreme

고성능 PC에서는 최대 규모와 최대 계산량을 목표로 한다.

필요하다면 특정 GPU를 위한 추가 가속 경로를 둘 수 있지만, 게임 규칙 자체가 특정 하드웨어에 종속되어서는 안 된다.

## 8. 성능 철학

컴퓨터가 아무리 빨라져도 모든 셀의 모든 속성을 모든 프레임에 계산하는 방식은 피한다.

### 공간적으로

- 움직이거나 반응하는 영역만 활성화
- 멀리 있는 영역은 더 거친 상태로 압축
- 필요할 때 다시 세밀하게 확장

### 시간적으로

- 모래 이동과 전기: 매우 빠르게
- 열/압력/화학: 중간 속도
- 식물/동물: 더 느리게
- 진화/문명/문화: 훨씬 느리게

### 의미적으로

모래에게 언어를 계산하지 않고, 소문에게 질량 충돌을 계산하지 않는다.

**필요한 시스템에만 참여시키는 구조**가 최종 규모를 가능하게 한다.

---

## 9. 콘텐츠 제작 철학

원소를 하나 추가할 때마다 수백 개의 조합을 손으로 작성하는 게임은 장기적으로 막힌다.

대신:

```text
fire + material[tag=organic]
when oxygen > threshold
→ ash + smoke + heat
```

같이 **이름이 아니라 속성·태그·환경 조건에 반응하는 법칙**을 중심으로 만든다.

특수한 예외는 일반 법칙보다 높은 우선순위로 둘 수 있다.

```text
fire + phoenix_egg → phoenix
```

이런 방식이면 새 물질이 기존 세계 규칙에 자동으로 참여할 수 있다.

---

## 10. 장기적으로 플레이어도 창조자가 된다

최종 콘텐츠 공급자는 개발팀만이 아니다.

플레이어가 만들고 공유할 수 있는 대상은:

- World
- Experiment
- Element Pack
- Rule Pack
- Species
- Machine
- Ecosystem
- Puzzle
- Timeline
- Mod

까지 확장될 수 있다.

더 나아가 최후반에는 플레이어가:

```text
물은 위로 흐른다
불은 차갑다
생명체가 죽으면 주변 시간이 느려진다
```

같은 **새로운 우주의 법칙**을 만들 수 있어야 한다.

---

## 11. 초기 개발에서 반드시 자제할 것

프로젝트가 야심차다는 이유로 시작부터 모든 것을 만들지 않는다.

초기에는 특히 다음을 한꺼번에 구현하지 않는다.

- 문명 전체
- 고급 AI NPC
- 멀티플레이
- 클라우드 시뮬레이션
- 1,000개 원소
- 완성형 모딩 플랫폼

초기 검증에 필요한 것은 훨씬 작다.

```text
재미있는 기본 물질
+ 온도
+ 압력/공기
+ 태그 기반 반응
+ 발견 시스템
+ 되돌리기/관찰
```

이 작은 세계에서 **예상하지 못한 재미있는 사건**이 충분히 나오면 그 위에 나머지를 쌓는다.

---

## 12. 실패 판정

다음 상태가 되면 방향을 재검토한다.

- 재료는 많지만 상호작용은 대부분 미리 정해진 1회성 애니메이션이다.
- 무엇이 일어날지 이미 다 알아서 관찰할 이유가 없다.
- 반대로 너무 랜덤해서 원인을 추론할 수 없다.
- 고급 시스템이 서로 영향을 주지 않는다.
- 새로운 원소를 넣을 때 기존 코드를 대량 수정해야 한다.
- 성능 때문에 상호작용 자체를 계속 삭제해야 한다.
- 초보자는 아무것도 이해할 수 없고, 고급 사용자는 할 일이 없다.

## 13. 성공 판정

이 프로젝트가 성공했다는 가장 좋은 장면은 다음과 같다.

플레이어가 어떤 세계를 만들었는데 개발자가 그것을 보고:

> **“우리는 저 현상을 직접 만든 적이 없는데, 우리 규칙들 때문에 저게 실제로 생겼다.”**

라고 말하게 되는 순간이다.

그리고 플레이어는:

> **“혹시 이것도 될까?”**

라는 생각 때문에 다시 세계에 손을 댄다.

그 질문이 계속 생기는 게임을 만든다.
